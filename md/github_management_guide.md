# 初心者向け GitHub Issues & Projects 活用・運用ガイド

GitHubを使い始めたばかりのチームや、プログラミング初心者同士で開発を円滑に進めるための、**「Issue（イシュー）の切り分け方」**や**「Projects（プロジェクト）でのタスク管理・運用方法」**をまとめたガイドです。

---

## 1. そもそも「Issue」と「Projects」とは？

初心者向けに一言で表すと以下のようになります。

- **GitHub Issues**: 開発における「やることカード（タスク）」です。バグの報告、新機能の提案、ドキュメントの作成など、すべての作業を1枚のカードとして起票します。
- **GitHub Projects**: Issues（やることカード）を「未着手」「進行中」「完了」などのホワイトボードに貼り付けて、プロジェクト全体の進捗を「見える化」するツールです。

---

## 2. 初心者向け：Issue of 切り分け方（タスクの分け方）

初心者が最も迷うのが「どれくらいの大きさ（粒度）でタスクを分ければいいのか」という点です。

### 💡 切り分けの黄金ルール：「1タスク＝半日〜1日以内で終わるサイズ」
Issueが大きすぎると、何から手をつけていいか分からず、作業が止まってしまいます。逆に細かすぎると管理が面倒になります。

*   ❌ **大きすぎる例（Bad）**: 「ゲームの戦闘システムを作る」
    *   *理由*: 敵の出現、攻撃処理、UI、勝敗判定など多くの要素が含まれており、終わるまでに数日〜数週間かかってしまいます。
*   ⭕ **適切に切り分けた例（Good）**:
    *   「プレイヤーが攻撃ボタンを押した時に攻撃アニメーションを再生する」
    *   「敵キャラクターにHPを設定し、攻撃が当たったらHPを減らす」
    *   「HPが0になった敵キャラクターを画面から消去する」

### 🔍 切り分ける手順
1.  **つくりたい機能を書き出す**: 実現したいことをノートやチャットにざっくり書き出します。
2.  **パーツに分解する**: 「画面（見た目）」「動き（プログラム）」「データ（素材や設定値）」のように分解します。
3.  **「これ以上分けられない最小単位」にする**: 1つの機能、1つの画面、あるいは1つのバグ修正レベルまで細分化します。

## 3. 初心者が迷わない「Issueの書き方」

Issueを開いたメンバーが「何をすればいいか」が一目でわかるように、簡単なテンプレートを決めておくと運用がスムーズになります。

### 📝 Issueの推奨テンプレート

```markdown
## 📌 目的 / 概要
<!-- 何のために、何を作るのかを簡潔に書きます -->
例: プレイヤーが攻撃したときに、敵にダメージを与えられるようにする。

## 🛠 やることリスト（ToDo）
<!-- 具体的な作業手順をチェックボックスで書きます -->
- [ ] 敵のスクリプトに `hp` 変数（初期値: 100）を追加する
- [ ] プレイヤーの攻撃判定が敵に当たった時のイベントを作成する
- [ ] 敵がダメージを受けた際、HPを `-10` する処理を追加する
- [ ] 動作確認を行い、HPが減っていることをログで確認する

## ✅ 完了定義（これができたらクリア！）
<!-- どんな状態になったらこのIssueを「Close（完了）」していいかの基準です -->
- プレイヤーの攻撃が当たった時、敵のHPが減ること
- 敵のHPが0になったら、敵が消滅すること
```

> [!TIP]
> **「完了定義（Definition of Done）」**を必ず書きましょう！初心者チームでは「どこまでやればこのタスクが終わりなのか」の認識がズレやすいため、クリア基準を明確にすることが最も重要です。

### 🏷 ラベル（Labels）の活用
Issueには、カテゴリを表す「ラベル」を貼りましょう。最初は以下の4〜5個があれば十分です。

- `bug` (赤色): 動かない、エラーが出るなどのバグ修正
- `enhancement` (青色): 新しい機能の追加や改善
- `documentation` (緑色): マニュアルやReadMeの作成・修正
- `good first issue` (黄緑色): **超簡単で、初心者が最初にやるのに適したタスク**
- `question` (紫色): わからないことの質問や相談用のIssue

## 4. GitHub Projects の設定とボードのつくり方

GitHub Projectsでは、**「カンバン（Kanban）」**形式のビューを使うのが最も直感的でおすすめです。

### 📋 基本の4カラム（列）構成
ボードには以下の4つの列を作ります。

1.  **Todo（未着手 / バックログ）**
    *   これからやるべきIssueを並べる場所。誰がやるかは決まっていてもいなくてもOK。
2.  **In Progress（進行中）**
    *   **「今、まさに自分が作業している」**タスクを置く場所。
    *   ⚠️ **ルール**: 1人が同時に In Progress に置くカードは最大2つまで（基本は1つ）にします。マルチタスクを防ぐためです。
3.  **Review（レビュー待ち）**
    *   プログラムが書き終わり、「他のメンバーに確認（テスト）してほしい」状態のタスクを置く場所。
4.  **Done（完了）**
    *   確認が終わり、完全にプロジェクトに反映（マージ）されたタスク。

## 5. 初心者チームを効率的に・楽しく動かす運用のコツ

プログラミング初心者が集まるチームでは、ツールを使うこと自体にプレッシャーを感じてしまうことがあります。以下の工夫を取り入れてみてください。

### ① 「自分でタスクを選ぶ」カルチャーにする
リーダーが一方的にタスクを割り当てる（アサインする）よりも、**「Todoにあるカードから、自分ができそうなものを自分で引き受ける（Assigneeに自分を設定する）」**方式がおすすめです。
自分で選ぶことで、「やらされている感」がなくなり、責任感とモチベーションが生まれます。

### ② まずは `good first issue` から始める
最初の数日は、プログラムを書かないような超簡単なIssueを用意します。
*   例: 「メンバー紹介ファイルに自分の名前を追加する」
*   例: 「ドキュメントの誤字を1箇所直す」
これによって、**「Issueを In Progress にする ➔ 作業する ➔ Pull Requestを作る ➔ レビューしてもらい Done にする」という一連のGitHubの流れを、プログラミングの難しさに邪魔されずに練習**できます。

### ③ 「進捗が出ない＝相談のチャンス」にする
毎日10分程度、または定期的なミーティングで、Projectsのボードを見ながら以下を話します。
*   「昨日やったこと」
*   「今日やること」
*   「**困っていること・詰まっていること（Blocker）**」
もし `In Progress` に数日間ずっと留まっているカードがあれば、「何か手伝えることはある？」と優しく声をかけ合える環境を作りましょう。

### ④ Issue / プルリクエスト（PR）の自動連携を使う
GitHubでは、プログラムを提出する「Pull Request（PR）」の本文に以下のように書くと、PRが承認（マージ）されたときに該当のIssueを自動で「Done（Close）」にしてくれます。

```markdown
Closes #12 （12番のIssueをクローズしますという意味）
```
手動でカードを動かす手間が省け、非常に効率的になります。

## 💡 次のアクション：まずやってみること
1.  GitHubのリポジトリの「Projects」タブから新規プロジェクトを「Board」テンプレートで作成する。
2.  「リポジトリのREADME.mdを修正する」という内容で、最初のIssue（ラベル: `good first issue`）を1つ作ってみる。
3.  そのIssueをご自身、またはメンバーの誰かに割り当てて、実際に Projects ボード上でカードを動かしてみる。
